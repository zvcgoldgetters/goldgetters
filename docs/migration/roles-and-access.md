# Payload roles and access policy

The migration maps Drupal capabilities to a small, explicit Payload role vocabulary. A user can hold multiple roles (`roles` JSON array field stored in a single atomic column on `users`, defaulting to `['member']` and saved to the JWT), so e.g. a playing treasurer holds `['member', 'treasurer']`. Administrator access is reserved for technical/deployment administration (`administrator` accounts and role assignments, `source-records`, and editorial cross-author overrides), while daily and yearly club operations live in the other roles.

| Payload role    | Intended capability                                                                                                                                                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `administrator` | Technical superadmin: full Payload administration, managing existing `users` (including `administrator` accounts, roles, deletion, and unlocking), `source-records`, and editorial overrides                                        |
| `director`      | Admin UI access + own account updates; manage yearly club & squad setup (`leagues`, `seasons`, `players`, `Players.user`, `club-settings`), list `users` & onboard non-`administrator` users, and read `teams`, `venues`, `matches` |
| `team-manager`  | Admin UI access + own account updates; manage matchday & scheduling (`matches`, `team-events`, `teams`, `venues`), RSVP workflows, and read `leagues`, `seasons`, `players`                                                         |
| `treasurer`     | Admin UI access + own account updates; manage private finance records (`bookings`) and read `seasons`, `players`, and `matches`                                                                                                     |
| `editor`        | Admin UI access + own account updates; read/create editorial content (`news`, `reports`, `previews`, `albums`, `media`), update/delete own records (`owner`, `uploadedBy`), and read `matches`                                      |
| `member`        | Admin UI access + own account updates + read-only `team-events` in `/admin`; read `matches`, `teams` (no contacts), `venues`, `players`; active linked players also read `bookings`                                                 |

## Implementation contract

- `payload/access/roles.ts` is the shared source for role values, display labels (`userRoleOptions`), deny-by-default wrappers, admin visibility helpers, and explicit role predicates.
- All collections and globals are deny-by-default for every operation (`read`, `create`, `update`, `delete`, `readVersions`, `unlock`, and `admin` on auth collections) using `createCollectionAccess`, `createAuthCollectionAccess`, `createGlobalAccess`, and the config-level `withDefaultDenyCollectionAccess` / `withDefaultDenyGlobalAccess` safeguards.
- Payload document locking (`payload-locked-documents`) is disabled across all collections and globals (`lockDocuments: false`) so authenticated members cannot read or manipulate locks on records they lack permission to edit.
- Access is granted only explicitly per operation (`allowRoles`, `allowRolesOrActivePlayer`, `hasAnyAssignedRole`, `isAdministrator`, `isDirector`, `isTeamManager`, `isTreasurer`, `isEditorial`, `isMember`, `allowUsersRead`, `allowUsersCreate`, `allowUsersUpdate`, `allowEditorialOwnerOrAdmin`), plus explicit field-level guards (`isAdministratorField`, `isDirectorField`, `isSelfOrDirectorField`, `canCreateUserRolesField`). Omitted operations default to `denyAll` (`() => false`), never Payload's built-in `Boolean(req.user)` fallback.
- Active linked players (`Players.user === req.user.id` with `status === 'active'`, checked via `isActiveLinkedPlayer` and cached per-request on `req`) receive read-only access to `bookings` (and hidden read-only `seasons` and `players` for relationship resolution). Users with `reserve`, `inactive`, or `historical` player status or without a linked active player record cannot read `bookings`.
- No collection permits anonymous REST reads; public frontend routes read via Next.js Server Components using the Payload Local API, filtering published state and selecting only public fields.
- Every authenticated user with at least one valid assigned role (`Users.access.admin: hasAnyAssignedRole`) can log into Payload Admin to read and update their own account (`email`, `password`, `displayName`). `director` can list `users`, create/onboard new non-`administrator` club users with non-`administrator` initial `Users.roles`, and manage `Players.user` links; modifying, role-updating, deleting, or unlocking other existing user accounts remains strictly `administrator`-only.
- Collections where a role only has read access are generally hidden from that role's Admin sidebar via `hideFromAdminUnlessRoles` (except `team-events`, which is shown read-only to `member`, and `bookings`, which relies on `Bookings.access.read` so `administrator`, `treasurer`, and active linked players see it in Admin while non-players and reserve/inactive/historical players do not), while relationship pickers and authorized API reads still function.
- Authentication alone is not sufficient for director, team-manager, treasurer, editorial, or administrative operations.
- Member-facing records must additionally scope reads and writes to the authenticated member or invitation token; the `member` role does not grant access to every member's private data.
- Sensitive fields (`Users.roles`, `Players.user`, `Teams.contactEmail`, and `Teams.contactPhone`) use explicit field-level access controls.
- Migration source metadata (`sourceId`, `sourceType`, `sourceUpdatedAt`, `targetCollection`, `targetId`, `importRun`) lives exclusively in the administrator-only `source-records` collection with a unique `(sourceType, sourceId)` constraint so raw Drupal IDs stay unique per record type and domain collections remain decoupled from migration bookkeeping.
- Editorial records use an immutable ownership field (`owner` on `news`, `reports`, `previews`, `albums`; `uploadedBy` on `media`) auto-assigned to the creating user, restricted to `administrator` on create, `denyAllField` on update, and preserved across bulk publishes and version restores; `allowEditorialOwnerOrAdmin` scopes `editor` `update`/`delete` access to that immutable owner while `administrator` can edit or delete any editorial record. Display credit fields (`author` on `news`, `reports`, `previews`; `photographer` on `albums`) default to the creator and remain editable by the record's owning editor or an administrator without changing edit ownership.
- Invitation-token endpoints must remain separately scoped and revocable as described in [RSVP design](rsvp.md).

This policy intentionally avoids recreating Drupal's permission matrix verbatim. Capabilities are grouped by the workflows that will be implemented in Payload, and collection-level checks remain the enforcement point for each private resource.
